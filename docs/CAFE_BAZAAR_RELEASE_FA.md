# راهنمای انتشار حساب‌یار در کافه‌بازار

این راهنما در ۲۵ تیر ۱۴۰۵ (۱۶ ژوئیه ۲۰۲۶) با مستندات رسمی توسعه‌دهندگان کافه‌بازار تطبیق داده شده است. چون قوانین و پیشخان ممکن است تغییر کنند، پیش از هر انتشار دوباره پیوندهای رسمی انتهای سند را بررسی کنید.

## وضعیت فعلی و موانع انتشار

کد از نظر شناسه برنامه، نسخه‌بندی، حریم خصوصی داخل برنامه و ساخت Release آماده‌سازی شده است؛ اما انتشار واقعی تا تکمیل موارد زیر مجاز و عملی نیست:

- [ ] حساب حقیقی یا حقوقی توسعه‌دهنده در پیشخان ساخته و فعال شود، قرارداد پذیرفته شود، اطلاعات ناشر کامل و اشتراک سالانه پرداخت شود.
- [ ] مدل قیمت‌گذاری پیش از اولین انتشار قطعی شود. طبق راهنمای بازار، تبدیل برنامه رایگان به پولی یا برعکس بعد از انتشار ممکن نیست. حساب‌یار در حال حاضر پرداخت درون‌برنامه‌ای ندارد.
- [ ] یک keystore دائمی با اعتبار حداقل ۲۵ سال ساخته و حداقل دو نسخه پشتیبان امن و جدا از Git نگهداری شود.
- [ ] SHA-256 گواهی همان کلید ثبت و secretهای انتشار تنظیم شوند.
- [ ] ایمیل و تلفن پشتیبانی واقعی در پیشخان وارد شوند.
- [ ] آیکون فروشگاه، تصویر سرصفحه و اسکرین‌شات‌های RTL بدون اطلاعات واقعی پرسنلی، مالی یا کارت آماده شوند.
- [x] تست کامل، بازبینی تصویری RTL و آزمون نصب/ارتقای محلی با همان کلید دائمی موفق شوند.
- [x] نامزد محلی دائمی‌امضای ۱.۴.۱ ساخته و package، نسخه، checksum، امضا، alignment و مجوزهای آن کنترل شود.
- [ ] نامزد خصوصی از `main` در workflow محافظت‌شده ساخته و همان فایل دقیق در VirusTotal، Play Protect و دستگاه فیزیکی certified تأیید شود.

هیچ commit، tag، push یا بارگذاری در پیشخان با این سند مجاز نمی‌شود؛ این عملیات فقط پس از اجازه صریح مالک انجام می‌شوند.

## هویت ثابت برنامه

| مورد | مقدار فعلی | قاعده آینده |
| --- | --- | --- |
| Application ID / Package Name | `com.hesabyar.garage` | پس از اولین انتشار هرگز تغییر نکند |
| نسخه توسعه‌ای | `1.4.1` | برای کاربر و یادداشت انتشار، مطابق SemVer؛ هنوز منتشر نشده |
| کد نسخه توسعه‌ای | `7` | در هر APK جدید حتماً بزرگ‌تر از همه نسخه‌های قبلی باشد |
| حداقل اندروید | API 26 / Android 8 | کاهش یا افزایش فقط با بررسی سازگاری کاربران |
| اندروید هدف | API 36 | پیش از انتشارهای آینده با الزام روز بازار بررسی شود |
| فرمت پیشنهادی این پروژه | APK امضاشده Release | برای اولین نسخه و آپدیت‌ها همان کلید دائمی |
| مجوز اینترنت | ندارد | افزودن شبکه فقط با تأیید محصول و بازبینی حریم خصوصی |

نام بسته و کلید امضا هویت نصب اندروید هستند. تغییر هرکدام باعث می‌شود کاربران نسخه قبلی نتوانند به‌روزرسانی را روی همان نصب دریافت کنند.

نسخه ۱.۴.۱ verification محلی را گذرانده است: نامزد دائمی‌امضا با SHA-256 برابر `74f54975b8fe902e3c2410244805bb7d17bc9e3c4666c9bd588645f1edde90fb` ساخته، کنترل و روی نسخه دقیق ۱.۴.۰ با حفظ داده ساختگی نصب درجا شد. قرارداد دادهٔ این نسخه Room 4 بدون تغییر ساختار یا migration جدید و backup schema 6 با پذیرش schemaهای 1 تا 6 است. اصلاح درآمد با بازسازی اتمیک ثبت‌های جدیدتر انجام می‌شود؛ حذف درآمد/انتقال/تسویه یک reversal حسابرسی‌شده با رمز دقیق برنامه است و رکورد و دلیل آن در تاریخچه می‌ماند. نامزد workflow محافظت‌شده، VirusTotal، Play Protect دستگاه فیزیکی و هر انتشار عمومی همچنان pending هستند.

## ۱. ساخت و نگهداری کلید دائمی

نمونه ساخت کلید با اعتبار ۱۰٬۰۰۰ روز:

```powershell
keytool -genkeypair -v `
  -keystore hesabyar-release.jks `
  -alias hesabyar `
  -keyalg RSA `
  -keysize 4096 `
  -validity 10000
```

الزامات نگهداری:

1. keystore و رمزهای آن را در Git، پیام‌رسان، ایمیل یا پوشه پروژه قرار ندهید.
2. دو نسخه پشتیبان رمزدار در محل‌های جدا نگه دارید و بازیابی آن‌ها را آزمایش کنید.
3. fingerprint عمومی گواهی را ثبت کنید:

```powershell
keytool -list -v -keystore hesabyar-release.jks -alias hesabyar
```

4. پنج secret زیر را در GitHub Actions تنظیم کنید:

| Secret | محتوا |
| --- | --- |
| `ANDROID_KEYSTORE_BASE64` | keystore به‌صورت Base64 تک‌خطی |
| `ANDROID_KEYSTORE_PASSWORD` | رمز keystore |
| `ANDROID_KEY_ALIAS` | alias کلید |
| `ANDROID_KEY_PASSWORD` | رمز کلید |
| `ANDROID_SIGNING_CERT_SHA256` | SHA-256 گواهی دائمی؛ با یا بدون `:` |

workflow آماده‌سازی علاوه بر صحت امضا، fingerprint را با مقدار pinشده مقایسه می‌کند و نامزد خصوصی را بدون انتشار عمومی نگه می‌دارد. workflow انتشار بعدی فقط همان فایل تأییدشده را دریافت می‌کند و در صورت استفاده از کلید یا هش اشتباه متوقف می‌شود.

## ۲. ساخت و کنترل APK بازار

برای build عمومی از task محافظت‌شده استفاده کنید. `assembleRelease` بدون متغیرهای امضا عمداً APK بدون امضا می‌سازد و خروجی عمومی محسوب نمی‌شود.

```powershell
$env:HESABYAR_KEYSTORE_PATH = 'C:\secure\hesabyar-release.jks'
$env:HESABYAR_KEYSTORE_PASSWORD = '<secret>'
$env:HESABYAR_KEY_ALIAS = 'hesabyar'
$env:HESABYAR_KEY_PASSWORD = '<secret>'

.\gradlew.bat clean testDebugUnitTest lintDebug assembleDebugAndroidTest assemblePublicRelease
```

پس از ساخت، این موارد را کنترل کنید:

```powershell
apksigner verify --verbose --print-certs app\build\outputs\apk\release\app-release.apk
aapt dump badging app\build\outputs\apk\release\app-release.apk
Get-FileHash app\build\outputs\apk\release\app-release.apk -Algorithm SHA256
```

- package باید دقیقاً `com.hesabyar.garage` باشد.
- `versionName` باید با نسخه و tag انتشار برابر باشد.
- `versionCode` باید از تمام بسته‌های قبلی بازار بزرگ‌تر باشد.
- SHA-256 signer باید با fingerprint دائمی ثبت‌شده برابر باشد و هرگز `Android Debug` نباشد.
- APK فعلی بسیار کمتر از سقف ۱۵۰ مگابایت بازار است؛ اندازه دوباره در هر نسخه کنترل شود.

### گیت اجباری Play Protect

پیام «Play Protect توسعه‌دهندهٔ این برنامه را نمی‌شناسد» در راهنمای رسمی کافه‌بازار در گروه **Uncommon / توسعه‌دهندهٔ ناشناخته** قرار دارد. این پیام به‌تنهایی نشانهٔ بدافزار یا خرابی امضا نیست و با امضای debug، تغییر package یا ساخت مکرر فایل حل نمی‌شود. تغییر کلید دائمی نیز ارتقای درجا را برای کاربران می‌شکند.

برای هر APK عمومی این مراحل اجباری است:

1. فایل نهایی را با کلید دائمی بسازید و package، نسخه، fingerprint و SHA-256 آن را ثبت کنید.
2. **دقیقاً همان فایل** را در VirusTotal بارگذاری کنید و نشانی گزارش شامل SHA-256 را نگه دارید.
3. اگر Play Protect نصب را مسدود یا دربارهٔ توسعه‌دهندهٔ ناشناخته هشدار داد، فرم رسمی [Play Protect Appeals](https://support.google.com/googleplay/android-developer/contact/protectappeals) را با package و SHA-256 همان فایل ارسال کنید.
4. اگر appeal لازم شد، طبق راهنمای بازار حداقل ۷ روز کامل برای بازبینی زمان بدهید؛ ممکن است Google ایمیل نتیجه نفرستد. تاریخ اعتراض و بازآزمایی باید تاریخ واقعی UTC، غیرآینده و قابل اثبات باشد.
5. همان فایل را با Play Protect روشن روی یک دستگاه فیزیکی certified نصب یا پس از appeal دوباره نصب کنید. تا وقتی نصب بدون هشدار انجام نشده، tag، GitHub Release یا درخواست انتشار بازار مجاز نیست.
6. نتیجه را در `release/v<version>/PLAY_PROTECT_APPROVAL.env` ثبت کنید. اگر آزمون نخست clear بود، مقدار `GOOGLE_APPEAL_SUBMITTED_AT` باید دقیقاً `not-required` باشد؛ در غیر این صورت تاریخ واقعی appeal ثبت می‌شود و بازآزمایی باید حداقل هفت روز بعد باشد. هر rebuild که SHA-256 را تغییر دهد، تأیید قبلی را باطل می‌کند و همه مراحل لازم باید برای هش جدید تکرار شوند.

Workflow دو مرحله‌ای است: `Prepare signed Play Protect candidate` فقط از شاخه `main` و محیط محافظت‌شده، APK تک‌امضاکننده با Signature Scheme v2 را به‌صورت artifact خصوصی می‌سازد؛ پس از VirusTotal، اعتراض در صورت نیاز و تست دستگاه، `Publish Play Protect-approved APK` هنگام tag همان artifact را با run ID، شناسه Workflow و نام ثبت‌شده دریافت می‌کند و بدون rebuild منتشر می‌کند. commit تگ باید داخل `origin/main` باشد و انتشار از محیط جداگانهٔ محافظت‌شده عبور کند. حالت `pending` یا کوچک‌ترین اختلاف در هش، نسخه، package، fingerprint، source commit یا provenance باعث توقف می‌شود. انتشار دستی با GitHub UI یا `gh release create` ممنوع است.

## ۳. اطلاعات و محتوای صفحه برنامه

پیشخان برای برنامه جدید این مراحل را دارد:

1. آپلود APK یا AAB؛
2. اطلاعات پایه شامل عنوان توسعه‌دهنده، نوع برنامه، دسته و قیمت‌گذاری؛
3. نام، توضیح کوتاه و توضیح کامل فارسی؛ اطلاعات انگلیسی اختیاری است؛
4. تلفن و ایمیل پشتیبانی و در صورت وجود وب‌سایت؛
5. آیکون، تصویر سرصفحه، اسکرین‌شات و محتوای پروموشن؛
6. بازبینی نهایی و انتخاب انتشار خودکار یا دستی پس از تأیید.

مشخصات اعلام‌شده در راهنمای رسمی پیشخان:

| دارایی | الزام |
| --- | --- |
| آیکون فروشگاه | حداقل `512×512`، حداکثر `3000×3000`، حداکثر ۳ مگابایت |
| تصویر سرصفحه | حداقل `720×288`، نسبت `5:2`، PNG، حداکثر ۱ مگابایت |
| تصویر پروموشن | حداقل `1152×648`، نسبت `16:9`، JPG، حداکثر ۱ مگابایت |

پیش‌نویس متن نسخه ۱.۴.۱ در [فایل آماده صفحه بازار](../release/v1.4.1/cafe-bazaar/LISTING_FA.md) قرار دارد. این متن تا ساخت و تأیید فایل نهایی فقط پیش‌نویس است. برای هر نسخه بعدی، material همان نسخه را زیر `release/v<version>/cafe-bazaar/` نگه دارید. سیاست عمومی نیز در [سیاست حریم خصوصی](PRIVACY_POLICY_FA.md) ثبت شده و همان محتوا داخل برنامه در دسترس است.

تمام تصاویر باید از نسخه Release نهایی، در RTL و با داده ساختگی گرفته شوند. نام، تلفن، مبلغ، شماره کارت و اطلاعات تعمیرگاه واقعی در دارایی‌های عمومی استفاده نشود.

## ۴. ارسال اولین نسخه در پیشخان

1. وارد پیشخان شوید و پس از فعال‌سازی حساب، «برنامه‌ها ← برنامه جدید» را انتخاب کنید.
2. APK امضاشده و کنترل‌شده را بارگذاری کنید.
3. اطلاعات پایه و قیمت‌گذاری قطعی را ثبت کنید.
4. متن‌ها، اطلاعات پشتیبانی و دارایی‌های تصویری را تکمیل کنید.
5. در «توضیحات بیشتر برای بررسی‌کننده» بنویسید برنامه کاملاً آفلاین است، مجوز اینترنت ندارد، فایل فقط با Storage Access Framework و انتخاب کاربر خوانده/نوشته می‌شود و متن حریم خصوصی در راه‌اندازی اولیه و بخش «بیشتر» قابل دسترسی است.
6. بازبینی نهایی را انجام دهید و درخواست انتشار بفرستید.

طبق راهنمای رسمی، بررسی معمولاً ۱ تا ۳ روز کاری طول می‌کشد و پنج‌شنبه و جمعه روز کاری محسوب نمی‌شوند. وضعیت و دلیل نیاز به تغییرات در پیشخان و ایمیل حساب توسعه‌دهنده نمایش داده می‌شود؛ Inbox و Spam هر دو بررسی شوند.

اگر درخواست صرفاً به اصلاح اطلاعات صفحه نیاز داشت و فایل برنامه تغییر نکرد، همان بسته و کد نسخه می‌تواند دوباره برای بررسی ارسال شود. اگر APK تغییر کرد، یک `versionCode` جدید و بالاتر بسازید.

## ۵. روند حرفه‌ای هر به‌روزرسانی

1. تغییرات و اثر آن‌ها بر Room، backup، امنیت و حریم خصوصی مشخص شوند.
2. `versionName` مطابق SemVer و `versionCode` دقیقاً یک واحد افزایش یابد.
3. migration و سازگاری backup برای تغییرات پایدار داده اضافه و روی نسخه قبلی آزمایش شوند.
4. تست، lint، build و بازبینی RTL اجرا شوند.
5. یادداشت فارسی «تغییرات این نسخه» و متن Release آماده شود.
6. workflow خصوصی آماده‌سازی از محیط محافظت‌شدهٔ `public-release-signing` و فقط روی HEAD شاخهٔ `main` اجرا شود؛ run ID، نام artifact، source commit و SHA-256 نامزد ثبت و همان فایل دانلود شود. محیط `public-release-publishing` و قانون محافظت از tagهای `v*.*.*` نیز باید با تأیید مالک فعال باشند.
7. همان APK نهایی در VirusTotal ثبت، در صورت نیاز appeal و روی دستگاه فیزیکی با Play Protect روشن کنترل شود؛ سپس رکورد exact-hash تکمیل شود.
8. tag فقط پس از تأیید نسخه و اجازه مالک push شود؛ workflow انتشار همان artifact را بدون rebuild دریافت و fingerprint، package، تطابق tag/نسخه، checksum و رکورد Play Protect را کنترل کند.
9. همان APK تأییدشده در «رهانش جدید» پیشخان بارگذاری و توضیحات فارسی همان نسخه ثبت شود.
10. بعد از تأیید، نصب درجا روی نسخه عمومی قبلی، حفظ داده و بازشدن مسیرهای اصلی کنترل شود.
11. شماره نسخه، کد نسخه، commit، fingerprint، SHA-256 فایل، نسخه Room/backup، گزارش VirusTotal و تاریخ بازار در سابقه انتشار ثبت شوند.

در صورت کشف باگ بعد از انتشار، بسته قبلی را با `versionCode` کمتر دوباره منتشر نکنید؛ نسخه patch جدید با کد بالاتر بسازید.

## ۶. رهانش تدریجی و پایش

قابلیت رهانش تدریجی بازار پس از رسیدن برنامه به حداقل ۵۰۰۰ نصب فعال قابل استفاده است و برای رهانش‌های اولیه در دسترس نیست. برای نسخه‌های پرریسک:

1. از ۵ یا ۱۰ درصد شروع کنید.
2. نصب، خطاها و نظرات همان نسخه را در پیشخان بررسی کنید.
3. در نبود مشکل بحرانی به ۲۵، ۵۰ و سپس ۱۰۰ درصد افزایش دهید.
4. پس از انتشار می‌توان درصد را افزایش داد، اما نمی‌توان آن را کاهش داد؛ در صورت مشکل رهانش را لغو و نسخه اصلاحی با کد بالاتر منتشر کنید.

لغو رهانش نسخه را از دستگاه کاربرانی که قبلاً آن را گرفته‌اند حذف نمی‌کند.

## ۷. چرا فعلاً APK و نه AAB

بازار هر دو فرمت را می‌پذیرد. AAB می‌تواند دانلود را برای دستگاه‌های متفاوت بهینه کند، اما بازار کلید خصوصی را ذخیره نمی‌کند و برای هر AAB باید فایل BIN متناظر با ابزار آفلاین Bundle Signer تولید و همراه همان باندل بارگذاری شود. حساب‌یار کوچک است و وابستگی native چندمعماری ندارد؛ بنابراین APK امضاشده برای شروع ساده‌تر و کم‌خطاتر است.

اگر در آینده حجم یا معماری برنامه استفاده از AAB را توجیه کرد، همان keystore اولین انتشار باید برای Bundle Signer استفاده شود و فایل BIN باید دقیقاً از همان AAB بارگذاری‌شده ساخته شود.
